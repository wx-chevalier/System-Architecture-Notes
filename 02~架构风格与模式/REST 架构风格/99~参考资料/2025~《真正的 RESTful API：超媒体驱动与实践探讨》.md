大多数 RESTful API 并非真正的 RESTful


谈论 REST 时，值得一读 Roy Thomas Fielding 的博士论文。那篇描述 RESTful 网络的原始论文 ——《架构风格与基于网络的软件架构设计》（Roy T. Fielding，2000 年），将表述性状态转移（REST）架构风格定义为一种用于设计可扩展、高性能和可维护网络系统（特别是 Web 服务）的框架。


该论文旨在分析基于网络的系统的架构风格，找出它们的优缺点。它将 REST 定义为一种针对现代 Web 优化的特定架构风格，侧重于可扩展性、简洁性和适应性。


Fielding 展示了 REST 原则如何成就了 Web 的成功，主张在设计具有通用、无状态接口和清晰的基于资源交互的分布式系统时采用 REST 原则。


在他的论文中，他并未规定要具体使用 HTTP 动词（如 GET、POST、PUT、DELETE），也没有像如今常见的那样专注于 CRUD 风格的 API。


这篇论文明确将 REST 描述为一种为构建基于网络的应用程序提供原则和约束的架构风格，并以 Web 作为其基本示例。


Roy Fielding 曾明确批评将 REST 过度简化为 CRUD 风格 API 的做法，他强调许多所谓的 “RESTful” API 未能实现关键的 REST 约束，特别是未能使用超媒体来驱动应用程序状态转换。在他 2008 年的博客文章《REST API 必须是超文本驱动的》中，他指出：


> “如果应用程序状态的引擎（因此也就是 API）不是由超文本驱动的，那么它就不可能是 RESTful 的，也不可能是 REST API。仅此而已。” 来源
>

这凸显了他的观点：没有超媒体控制，一个 API 就不符合 REST 架构风格。超媒体控制是嵌入在资源表示中的元素，用于指导客户端接下来可以执行哪些操作。


在人们对 REST 的理解中，常见的误解有：




*   REST 就是 CRUD（通常情况下是，但并非总是如此）


*   资源是一个实体（通常指持久化实体）


*   RESTful API 不能使用动词


但这些实际上是 API 设计者针对特定 API 做出的设计决策，与 REST 本身并无关系。


“由超文本驱动” 意味着什么？



Roy Fielding 批评中提到的 “不由超文本驱动”，指的是许多声称是 RESTful 的 API 中缺少超媒体作为应用程序状态引擎（HATEOAS）。HATEOAS 是 REST 的一项基本原则，它要求客户端通过服务器响应中嵌入的超媒体链接动态发现操作和交互方式，而不是依赖于带外知识（例如 API 文档）。




```
{


&#x20; "orderId": 123,


&#x20; "\_links": {


&#x20;   "self": { "href": "/orders/123" },


&#x20;   "cancel": { "href": "/orders/123/cancel", "method": "POST" }


&#x20; }


}
```

它解决的核心问题是客户端 - 服务器耦合。可能有无数项目因为服务器 URI 结构的微小变化，就需要协调（而且往往是痛苦地）部署多个客户端应用程序。HATEOAS 驱动的方法通过将客户端与服务器的命名空间解耦，直接解决了这个问题。这提高了系统的可演化性。


简单地实现 HATEOAS 会让你更接近 RESTful 原则，而不是纠结于 API 中是否允许使用动词。


什么是 “资源”？



人们经常争论 REST 中的资源是什么。我或多或少都见过有人认为资源是来自服务器的数据结构，不幸的是，他们常常甚至将其等同于持久化实体。


让我们看看 Fielding 对此的说法：


REST 中信息的关键抽象是资源。任何可以命名的信息都可以成为资源：一份文档或图像、一项临时服务（例如 “洛杉矶今天的天气”）、其他资源的集合、一个非虚拟对象（例如一个人）等等。换句话说，任何可能成为作者超文本引用目标的概念都必须符合资源的定义。资源是到一组实体的概念映射，而不是在任何特定时间点与该映射相对应的实体。


语义是分配资源标识符并为这些资源填充表示形式这一行为的副产品。服务器或客户端软件在任何时候都不需要知道或理解 URI 的含义 —— 它们仅仅是作为一种渠道，资源的创建者（一个人类命名权威）可以通过它将表示形式与 URI 所标识的语义相关联。换句话说，服务器上没有资源；只有通过由资源定义的抽象接口提供答案的机制。这可能看起来有些奇怪，但这正是 Web 能够在众多不同实现中正常工作的本质。


现在让我们看看 RFC 3986 的内容：


本规范并未限制资源的范围；相反，“资源” 一词被广泛用于指代任何可以通过 URI 标识的事物。常见的例子包括电子文档、图像、具有特定用途的信息源（例如 “洛杉矶今天的天气报告”）、服务（例如 HTTP 到 SMS 的网关）以及其他资源的集合。资源不一定能通过互联网访问；例如，人、公司和图书馆中的实体书籍也可以是资源。同样，抽象概念也可以是资源，例如数学方程的运算符和操作数、关系类型（例如 “父母” 或 “员工”）或数值（例如零、一和无穷大）。

关于资源的结论



资源几乎可以是任何可以通过 URI 寻址的事物。它可以是一个物理对象、一个概念、一份文档、一项服务，甚至是一个虚拟的或抽象的事物 —— 只要它可以被唯一标识和表示。

我对越来越多的人将任何基于 HTTP 的接口称为 REST API 感到沮丧。


Fielding 描述了在称你的 API 为 RESTful API 之前应该考虑的六条规则 来源。


API 设计者们，在称你的成果为 REST API 之前，请注意以下规则：




1.  REST API 不应依赖于任何单一的通信协议，尽管它能否成功映射到特定协议可能取决于元数据的可用性、方法的选择等。一般来说，任何使用 URI 进行标识的协议元素都必须允许使用任何 URI 方案进行标识。\[如果做不到这一点，就意味着标识与交互没有分离。]


2.  REST API 不应对通信协议做任何修改，除非是完善或修正标准协议中未明确规定的细节，例如 HTTP 的 PATCH 方法或 Link 头字段。针对有缺陷的实现的变通方法（例如那些愚蠢地认为 HTML 定义了 HTTP 方法集的浏览器）应该单独定义，或者至少放在附录中，并期望这种变通方法最终会过时。\[如果做不到这一点，就意味着资源接口是特定于对象的，而不是通用的。]


3.  REST API 应该将几乎所有的描述精力都用于定义用于表示资源和驱动应用程序状态的媒体类型，或者用于为现有的标准媒体类型定义扩展的关系名称和 / 或支持超文本的标记。任何用于描述在哪些感兴趣的 URI 上使用哪些方法的努力，都应该完全在媒体类型的处理规则范围内定义（而且在大多数情况下，已经由现有的媒体类型定义好了）。\[如果做不到这一点，就意味着是带外信息在驱动交互，而不是超文本。]


4.  REST API 不得定义固定的资源名称或层次结构（这显然会导致客户端和服务器的耦合）。服务器必须有控制自己命名空间的自由。相反，应该允许服务器指导客户端如何构造适当的 URI，例如像 HTML 表单和 URI 模板那样，通过在媒体类型和链接关系中定义这些指令来实现。\[如果做不到这一点，就意味着客户端由于带外信息（例如特定领域的标准）而假设了资源结构，这与 RPC 的功能耦合在数据导向方面是等价的。]


5.  REST API 不应有对客户端有意义的 “类型化” 资源。规范作者可以使用资源类型来描述接口背后的服务器实现，但这些类型必须与客户端无关且对客户端不可见。对客户端有意义的唯一类型是当前表示的媒体类型和标准化的关系名称。\[同上]


6.  进入 REST API 时，除了初始 URI（书签）和一组适合目标受众的标准化媒体类型（即预期可能使用该 API 的任何客户端都能理解的媒体类型）之外，不需要有任何先验知识。从那时起，所有应用程序状态转换都必须由客户端对服务器提供的选项的选择来驱动，这些选项存在于接收到的表示中，或者由用户对这些表示的操作所暗示。转换可能由客户端对媒体类型和资源通信机制的了解来决定（或限制），而这两者都可以动态改进（例如按需代码）。\[如果做不到这一点，就意味着是带外信息在驱动交互，而不是超文本。]

规则的解读

### 1. 不依赖单一协议&#xA;

REST API 使用统一资源标识符（URI）来命名事物。URL（http://…）只是 URI 的一种特定类型，它还包含了位置信息。这里的关键原则是，资源的基本标识应该与其访问机制分离。


URI（统一资源标识符）是一个宽泛的概念，指任何用于标识资源的字符串，而 URL（统一资源定位符）是 URI 的一种特定类型，它不仅标识资源，还通过描述其主要访问机制（例如其网络位置）提供了定位该资源的方法。


你的 API 应该能够与任何 URI 一起工作，而不依赖于特定于 HTTP 的机制。


### 2. 不修改协议&#xA;

遵循现有的标准（如 HTTP）。如果标准中的某些内容不明确，可以进行澄清。不要发明新的行为或破坏现有的行为。


不要随意修改或重新定义 HTTP 的工作方式。可以填补空白，但不要改变规则。


如果 HTTP 没有完全定义 PATCH 应该如何工作，你可以进行澄清。但不要仅仅因为方便就将 GET 重新定义为也能删除数据。


### 3. 关注媒体类型，而非 URI&#xA;

你的 API 应该定义如何理解和使用它返回的数据 —— 通过媒体类型（如 JSON、HTML）和链接 —— 而不是关注 URI 的结构或要调用的操作。


把精力放在设计数据的格式和其中的链接上，而不是记录要访问哪些 URL。


不要去文档化必须向 `/users/123/activate` 发送 POST 请求，你的 API 应该以支持超媒体的格式（如 `application/hal+json` 或自定义类型如 `application/vnd.myapp.user+json`）返回用户表示。




```
{


&#x20; "name": "John Doe",


&#x20; "status": "inactive",


&#x20; "\_links": {


&#x20;   "self": { "href": "/users/123" },


&#x20;   "activate": { "href": "/users/123/activate", "method": "POST" }


&#x20; }


}
```

客户端代码不知道 `/users/123/activate` 这个路径。它只知道媒体类型定义了一个 “activate” 链接关系，并使用响应中提供的 href 和 method 来执行操作。


### 4. 不要硬编码 URI 结构&#xA;

这条规则是规则 3 的直接结果。客户端不应该假设或硬编码像 `/users/123/posts` 这样的路径。相反，它们应该通过服务器提供的链接来发现 URI。客户端应该动态地了解 URI。

### 5. 避免资源 “类型”&#xA;

服务器对资源的内部分类（例如用户与管理员）必须完全与客户端无关且对客户端不可见。


客户端不应该关心资源在内部代表什么样的实体（如用户、管理员、版主）。它只应该关心媒体类型（如 `application/json`）和它所看到的链接 / 操作。


不要暴露内部对象类型或角色。只需发送带有有用链接的结构良好的响应。不要要求客户端知道某个资源是管理员类型。只需给它们一个一致的 `application/json` 响应，其中包含相关的链接和数据。


他所说的 “标准化关系名称” 指的是 IANA 注册的链接关系。


### 6. 从一个书签开始，然后跟随链接&#xA;

客户端只需要一个起点（例如一个基础 URL、一个书签）和对标准媒体类型的了解。其他所有内容 —— 该做什么、去哪里 —— 都应该来自服务器的响应。


客户端应该像浏览网站一样跟随链接 —— 从主页开始，然后点击进入，而不是硬编码路径。


从 [https://api.example.com/](https://api.example.com/) 开始，然后跟随每个响应中的 \_links：

为什么大多数 API 不是真正的 RESTful 的？



一种更简单的、类 RPC 风格在 HTTP 上的广泛采用，可能要归因于工具和开发体验方面的实际权衡：围绕 OpenAPI 等规范的生态系统迅速发展，提供了立竿见影的好处，这对开发团队来说是不可抗拒的。这些工具提供了强大的功能，如自动客户端 / 服务器代码生成、交互式文档和请求验证等。对于一个面临交付压力的团队来说，OpenAPI 定义提供的清晰、静态的契约过去是，现在可能仍然常常被视为 “足够好”，这使得 HATEOAS 的长期架构优势（如可演化性）显得抽象且不那么紧迫。


此外，构建一个真正由超媒体驱动的客户端的初始认知负担被认为是一个重大障碍。对开发人员来说，阅读文档并硬编码像 `/users/{id}/orders` 这样的 URI 模板，似乎比编写一个能够动态解析 `_links` 部分并在运行时发现 “orders” URI 的客户端更容易。


在许多常见场景中，例如前端单页应用程序与后端由同一个团队开发，客户端和服务器已经紧密耦合。在这种情况下，HATEOAS 解决的主要问题 —— 将客户端与服务器的 URI 结构解耦 —— 并没有成为一个紧迫的痛点，这使得更简单的、由文档驱动的方法成为阻力最小的路径。


结论



Fielding 的规则强调，真正的 RESTful API 应该采用超媒体（HATEOAS）作为交互的核心机制，而不仅仅是将 HTTP 用作传输工具。REST 在本质上是与协议无关的；HTTP 只是一种方便的实现方式。客户端应该通过嵌入在表示中的链接和标准化关系来动态发现和导航资源，而不是依赖硬编码的 URI 结构、类型或外部文档。


这使得 REST 系统松耦合、可演化，并且与 Web 本身的运作方式一致：通过表示、发现和状态转换。REST 并不是关于通过 HTTP 暴露你的内部对象模型 —— 而是关于构建行为类似于 Web 的分布式系统。


因此，简单点说就是要务实。出于本文中给出的原因，我个人喜欢避免使用 “RESTful” 这个术语，而是说 “基于 HTTP” 的 API。构建任何对你的项目和 API 的消费者有意义的东西。不要理会那些宣扬 RESTful API 应该是什么样、不应该是什么样的教条主义者。一个 API 首先应该易于学习且难以误用。如果它满足这个标准，那么它是否是 RESTful 的并不重要。如果适合你的情况，就遵循 Postel 定律：“严于律己，宽以待人。”


你的 API 的消费者是谁？他们学习和使用这个 API 会有多容易？它使用起来会直观吗？可能存在哪些约束？你如何对它进行版本控制？有哪些弃用和淘汰策略？如何有效地将 API 的变更传达给消费者？这些事情比你的资源标识符的实际格式重要得多。


通过在资源表示中使用 HATEOAS 并引用模式定义（如 XSD 或 JSON Schema），你可以使客户端能够理解数据的结构并动态导航 API。这可以支持通用的或自适应的客户端。如果这与你的目标（例如客户端解耦、可演化性、动态交互）一致，那么这是一个有效且强大的设计选择。如果你正在为不受你控制的外部开发人员构建公共 API，那么投入精力实现 HATEOAS 是值得的。如果你正在为自己团队控制的单个前端构建后端，那么更简单的 RPC 风格 API 可能是更实际的选择。
